# Пост-обработка GPS-трека

При окончании записи трека выполняется пост-обработка. Обработка запускается сразу после завершения записи; в память сохраняется **обработанный** трек.

Фильтрация выполняется **строго последовательно**. На вход подаётся массив сырых точек, полученных от `CLLocationManager`.

## Конвейер

```
Сырой трек ([CLLocationCoordinate2D])
  → Фильтр шума (окно: 33 точки)
  → Оптимизация RDP (порог: 5 м)
  → Алгоритм Чайкина (1 итерация)
  → Итоговый сглаженный трек
```

## Параметры по умолчанию

Параметры фильтров заданы в системе по умолчанию, но пользователь может изменить их на экране настроек.

| Этап | Состояние | Параметр | Тип |
|------|-----------|----------|-----|
| Фильтр шума | Включён | `windowSize = 33` | `Int` |
| RDP (оптимизация) | Включён | `tolerance = 5.0` | `Double` (метры) |
| Алгоритм Чайкина | Включён | `iterations = 1` | `Int` |

## Алгоритмы (Swift)

### 3.1. Шумоподавление (Moving Average / скользящее среднее)

**Вход:** массив точек, размер окна `N` (дефолт: 33).

**Логика:** для каждой точки с индексом `i` рассчитывается среднее арифметическое широты (`latitude`) и долготы (`longitude`) среди `N` соседних точек (слева и справа от текущей).

**Краевые условия:** для первых и последних `N/2` точек трека, где окно выходит за пределы массива, применяется уменьшенное симметричное окно или координаты остаются исходными — чтобы не сдвигать начальную и конечную точки.

### 3.2. Оптимизация (RDP — Ramer–Douglas–Peucker)

**Вход:** массив после фильтра шума, порог `tolerance` в метрах (дефолт: 5.0).

**Логика:** рекурсивный алгоритм находит точку, максимально удалённую от прямой между первой и последней точками сегмента.

**Важно:** расстояние от точки до отрезка считается с учётом кривизны Земли (метрическое расстояние Хаверсина), а не в плоских декартовых координатах.

- если максимальное расстояние **меньше** `tolerance` — промежуточные точки удаляются;
- если **больше** — трек делится в этой точке, алгоритм вызывается рекурсивно для обеих половин.

### 3.3. Сглаживание Чайкина (Chaikin's Algorithm)

**Вход:** массив после RDP, количество итераций `L` (дефолт: 1).

**Логика:** алгоритм обходит все отрезки полилинии и для каждого сегмента добавляет две новые точки:

- \(Q_i = 0.75 \cdot P_i + 0.25 \cdot P_{i+1}\)
- \(R_i = 0.25 \cdot P_i + 0.75 \cdot P_{i+1}\)

**Начальная и конечная точки** (старт/финиш) остаются неизменными. При `iterations = 1` операция выполняется один раз.

## Производительность и потоки

Длинный трек может содержать десятки тысяч точек. Фильтрация с окном в 33 точки и рекурсия RDP — ресурсоёмкие операции.

| Требование | Описание |
|------------|----------|
| Запрет блокировки UI | Конвейер **не выполняется** на главном потоке (Main Thread) |
| Асинхронность | Обработка в фоне: `Task` или `DispatchQueue.global(qos: .userInitiated)` |
| Память | Для точек используются `struct`, чтобы избежать оверхеда ARC от классов |
